# Verifying SyncTV backend rules

Run from the workspace root with the official Verus release `0.2026.11.22.1ce6a59` for your platform. Its archive includes the solver, the verified standard library and the launcher. Install the matching Rust toolchain alongside the workspace nightly.

```sh
rustup toolchain install 1.100.0 --profile minimal
make verify VERUS=/path/to/extracted/verus
```

With the launcher on your PATH, use `make verify`. The CI job checks the Linux archive's SHA-256 digest and runs the same target. When upgrading, update the release, digest and matching Rust version together and recheck every proof. [Official release](https://github.com/verus-lang/verus/releases/tag/release/0.2026.11.22.1ce6a59)

## Why verify these rules

Rust checks ownership and types. SyncTV also needs properties such as “removing a permission wins even when the same bit is granted” and “every admitted read fits both the declared message and the remaining budget.” These decisions have small inputs and enormous input spaces. They run on authentication, connection admission and media delivery paths where a wrong answer affects access or availability.

Amazon's binary-search example specifies both success and failure. A contract that only constrains successful lookups would let an implementation reject every lookup. SyncTV uses two-sided contracts for admission, expiration, range resolution and repair. Protocol parsers additionally need a mathematical description of the value consumed, since a parser can stay within bounds and still return the wrong length. [Amazon Science article](https://www.amazon.science/blog/developing-provably-correct-rust-code-with-verus)

The article also uses lock invariants to reason about custom synchronization. SyncTV's workspace denies unsafe Rust by default. Its connection manager combines atomics with separate room and actor registries, and its cache fences cross PostgreSQL and Redis. An end-to-end concurrency proof would need to model when each reservation becomes visible, how cancellation releases it, and which storage operations are atomic. The contracts here cover the decisions made from each observed state. They leave the behavior of the locks and remote stores to their implementations and integration tests.

## Maintaining a proof

`lib.rs` includes the same source files that Cargo builds for the services. Keep executable decisions shared between builds. Attach `verus_spec` to those functions and place mathematical definitions and proof hints under `cfg(verus_only)`. Cargo builds need no Verus dependency. CI passes `--no-cheating`, which rejects proof shortcuts such as `assume`, `admit` and trusted external bodies.

Use an independently reviewable specification for the property at risk. The permission proofs compare dual-mode conversions to fixed wire layouts. The QUIC decoder and decimal scanner relate each loop iteration to recursive definitions over mathematical integers and sequences. Loop invariants prove indexing and arithmetic safety, and decreasing measures establish termination. At an I/O boundary, add a regression test that exercises the real caller and passes the resulting values to the verified function. [Executable annotations](https://verus-lang.github.io/verus/guide/exec_attr.html) · [Dual-mode specifications](https://verus-lang.github.io/verus/guide/exec_to_spec.html) · [Bit-vector proofs](https://verus-lang.github.io/verus/guide/bitvec.html)

The MFA proof uses sequence membership and the standard library’s sequence lemmas to connect a prefix loop invariant to the complete list. The encoded-path contract uses quantifiers for both existence and earliest match. The email retry proof relates a bounded accumulator to the mathematical sum modulo five and uses bit-vector reasoning for the backoff factor. [Sequence lemmas at the pinned release](https://github.com/verus-lang/verus/blob/1ce6a59/source/vstd/seq_lib.rs) · [Quantifiers and triggers](https://verus-lang.github.io/verus/guide/forall.html)

The RTMP contract follows the parser/serializer approach used by Vest. The executable codec refines a specification over byte sequences. A separate framing lemma covers any following payload and any incomplete prefix. Upload planning uses a quantified loop invariant and Euclidean division to relate each generated part and each accepted range to the same layout. [Vest](https://github.com/secure-foundations/vest) · [Verus sequence library](https://github.com/verus-lang/verus/blob/1ce6a59/source/vstd/seq_lib.rs)

Anvil models cluster transitions and dependencies between controllers to reason about eventual progress. CapybaraKV models persistent storage to reason about crashes. SyncTV's timing and upload contracts cover local decisions. Claims about eventual leadership or recovery of a partially completed upload would also require explicit network, storage and failure models. [Anvil](https://github.com/anvil-verifier/anvil) · [CapybaraKV](https://github.com/microsoft/verified-storage)

Verdict verifies X.509 certificate validation against specific chain policies. SyncTV delegates certificate processing to its TLS dependencies. Its origin contract covers host, port and scheme comparison after parsing. Atmosphere verifies microkernel memory and synchronization primitives. SyncTV uses the synchronization provided by Rust libraries and Tokio, whose scheduling and cancellation behavior is outside these proofs. [Verdict](https://github.com/secure-foundations/verdict) · [Atmosphere](https://mars-research.github.io/projects/atmo/)

The trusted base includes the intended contract, Verus, Z3, library specifications and the Rust compiler. A successful run establishes the stated contracts. The verifier's reported count includes constants and proof helpers. Service tests still exercise the wiring, and integration and concurrency tests cover behavior across the boundaries above.
