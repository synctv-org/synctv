## 先定位层级

不要一开始就翻所有配置项。先把问题归到一个层级，再执行对应命令。

<CardGrid>
  <Card title="进程没起来" icon="rocket">
    先看配置校验、必填 secret、数据库连接、Redis 依赖和端口占用。
  </Card>
  <Card title="能启动但访问异常" icon="setting">
    先看 readiness、反向代理、CORS、可信代理、Ingress、HTTP/gRPC 协议和端口映射。
  </Card>
  <Card title="登录或账号异常" icon="approve-check-circle">

  </Card>
  <Card title="媒体播放异常" icon="puzzle">

  </Card>
</CardGrid>

## 错误文本速查

| 看到的错误或现象 | 常见原因 | 处理动作 |
| --- | --- | --- |
| `jwt.secret` 是占位值或太弱 | 生产环境仍使用默认 secret | 生成 `openssl rand -base64 32`，写入 secret 或 `.env.synctv` |
| `opaque_server_setup_secret` 为空或无效 | OPAQUE 长期 secret 没配置 | 生成 `openssl rand -base64 48`，保存后不要随部署变化 |
| `credential_encryption_key` 格式错误 | 不是 64 个十六进制字符 | 使用 `openssl rand -hex 32` 重新生成 |
| `required variable ... is missing` | 生产 Compose 缺 `.env.postgres` 或 `.env.synctv` | 运行 `./scripts/init-compose-env.sh` 并填写 root 密码 |
| `/health/ready` 非 200 | 数据库、Redis、ticket 后端或服务依赖未就绪 | 看 readiness 响应和第一条服务日志 |
| 浏览器报 CORS | origin 未配置、填了 path、代理未放行 OPTIONS | 只把真实 origin 写入 `server.cors_allowed_origins` |
| gRPC Ingress 失败但 HTTP 正常 | gRPC 没有独立 Ingress 或缺 backend protocol | 给 gRPC Ingress 设置 `nginx.ingress.kubernetes.io/backend-protocol: "GRPC"` |
| `synctv system stats` 连不上 | management endpoint、Unix socket、TCP token 或环境变量错误 | 检查 `management.*` 和 `SYNCTV_MANAGEMENT_ENDPOINT` |
| WebSocket 401/403 | token 过期、ticket 过期、不是房间成员、origin 被拒绝 | 重新申请 ticket，确认成员关系和 CORS/WebSocket origin |
| OAuth2 callback/state 错误 | redirect URL 不一致或多副本未共享 Redis | 对齐 runtime settings 和第三方平台登记值，多副本配置 Redis |
| WebAuthn/passkey 失败 | `rp_origin` 与实际 HTTPS origin 不一致 | 配置真实 origin，确认 `rp_id` 是同域或父域 |
| Range seek 或代理播放异常 | Provider header 不完整或上游不支持 Range | 检查 Provider 返回 header 和上游 `Accept-Ranges` |
| HLS 多副本偶发 404 | publisher 节点不可达或存储模型不一致 | 使用 publisher-node proxy、共享文件系统或 OSS |

## 常用命令模板

### readiness

```bash
curl -i http://localhost:8080/health/ready
```

预期是 `HTTP/1.1 200 OK`。如果不是 200，先看响应体，再看服务日志中第一条错误。

### CORS 预检

```bash
curl -i \
  -X OPTIONS \
  -H 'Origin: https://app.example.com' \
  -H 'Access-Control-Request-Method: POST' \
  http://localhost:8080/api/auth/login
```

预期响应包含：

```http
Access-Control-Allow-Origin: https://app.example.com
```

如果返回的 origin 不对或没有该 header，检查 `server.cors_allowed_origins`。值必须是 origin，不能带路径。

### 登录接口错误体

HTTP API 的错误体形状是：

```json
{
  "error": "Invalid username or password",
  "status": 401,
  "code": null,
  "request_id": "..."
}
```

客户端应优先按 HTTP 状态码和可选 `code` 处理，不要只匹配 `error` 文本。

### Provider Range 检查

```bash
curl -I -H 'Range: bytes=0-1023' 'https://upstream.example.com/video.mp4'
```

常见预期：

- 支持 Range：`206 Partial Content`，并有 `Content-Range` 或 `Accept-Ranges`。
- 不支持 Range：返回 `200 OK`。这种上游不适合 slice cache，SyncTV 会绕过缓存，不做 full-body cache。

## 配置类问题

配置问题优先用命令确认最终值，不要只看 YAML 文件。环境变量和 CLI 参数可能覆盖 YAML。

```bash
synctv --config /etc/synctv/synctv.yaml config show --output yaml
synctv --config /etc/synctv/synctv.yaml config validate
```

如果最终配置和你预期不一致，按顺序检查：

- 是否加载了正确的配置文件。
- `.env` 是否被加载，或者是否用了 `--no-dotenv`。
- 环境变量是否覆盖了 YAML。
- `*_file` secret 路径是否相对配置文件目录，而不是 `data_dir`。
- `data_dir` 是否只影响运行时输出路径。

详细规则见 [配置文件如何工作](../../configuration/how-configuration-works/)。

## 部署类问题

### Docker Compose

生产 Compose 会要求 Compose 文件目录存在填好的 `.env.postgres` 和 `.env.synctv`，这是预期行为。先按 [Docker Compose 部署](../../deployment/docker-compose/#获取生产-compose-文件) 获取 `docker-compose.yml` 和初始化脚本；不要为了让服务启动而把弱 secret 写入 compose 文件。

```bash
./scripts/init-compose-env.sh
# 填写 .env.synctv 中的 SYNCTV_BOOTSTRAP_ROOT_PASSWORD，然后检查渲染结果。
docker compose config
docker compose up -d
```

更多内容见 [Docker Compose 部署](../../deployment/docker-compose/)。

### Helm

Helm 渲染成功只代表 Kubernetes manifest 语法成立，不代表业务配置安全。生产上线前仍要看启动日志，确认配置校验通过。

重点检查：

- HTTP 和 gRPC 是否是两个独立 Service。
- HTTP 和 gRPC 是否是两个独立 Ingress。
- gRPC Ingress 是否有独立 annotation。
- metrics ServiceMonitor/VMServiceScrape 是否抓对 Service。
- 多副本 HLS 是否使用共享存储。
- `existingSecret` 是否包含 chart 需要的全部 key。

更多内容见 [Helm 部署](../../deployment/helm/)。

## 认证与账号问题

本地两步验证只在 password、webauthn/passkey、verified email 这些本地验证方式之间生效。OAuth2 不参与本地 2FA，但开启 2FA 的用户仍然可以使用 OAuth2 登录。

如果用户开启 2FA 后登录异常，检查：

- 用户是否仍有至少两种可用本地验证方式。
- 邮箱作为第二因素时，SMTP 是否可用。
- passkey 作为第二因素时，WebAuthn origin 是否正确。
- 刷新 token 是否来自满足当前 2FA 策略的登录上下文。

## 需要收集哪些信息

提交问题或内部排查时，建议收集：

- SyncTV 版本和部署方式。
- `synctv config show --output yaml` 的输出。提交前删除敏感值，即使命令会打码，也要复查。
- `synctv config validate` 的完整错误。
- Compose/Helm 渲染结果中相关 Service、Ingress、ConfigMap 和 Secret key 名称。
- 服务日志中第一个错误，而不是最后一个级联错误。
- 触发问题的客户端请求路径、方法、状态码和必要 header。不要提交 token、cookie、密码、SMTP 密码或 provider 凭据。

<Aside type="caution">
不要把 Secret 值、JWT、OAuth2 code、Cookie、Provider token、SMTP 密码或数据库 URL 明文贴到 issue、聊天窗口或日志系统。
</Aside>
