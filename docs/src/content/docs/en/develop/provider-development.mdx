A Provider implementation spans the upstream protocol, Core model, public APIs, remote transport, CLI, App, and tests. Each Provider keeps its own protocol model and capabilities while sharing stable SyncTV core contracts.

## Design Principles

1. **One model boundary per Provider.** Keep DTOs, URL parsing, signing, pagination, login, playback formats, and error mapping in that Provider module.
2. **Model actual upstream capabilities.** Video sites, live platforms, media servers, and NAS systems keep their own source, target, pagination, and playback metadata.
3. **Reuse stable core contracts.** `MediaProvider`, `DynamicPlaylistProvider`, `PlaybackResult`, `SourceConfig`, `ProviderTarget`, credential repositories, and transport actions are shared boundaries.
4. **Carry typed configs through discovery and creation.** Parse, resolve, list, search, and preview results return media or playlist source configs that clients can submit directly.
5. **Resolve every generated URL.** Stream, manifest, segment, subtitle, danmaku, thumbnail, and cover URLs need matching resolvers and tests.
6. **Keep local and remote behavior aligned.** Embedded clients, remote-provider gRPC, and public SyncTV HTTP/gRPC expose the same business semantics.

<Aside type="note" title="Upstream research">
  Clone reference implementations into a separate `provider-references` directory and record the commit. Port protocol, signing, and response mapping into Rust. Runtime behavior remains inside SyncTV's Provider module.
</Aside>

## Layer Map

| Layer | Primary location | Responsibility |
| --- | --- | --- |
| Upstream client | `synctv-media-providers/src/<provider>/` | HTTP/WebSocket protocol, signing, private DTOs, upstream pagination, playback resolution |
| Internal remote protocol | `synctv-media-providers/proto/`, `src/grpc/`, `src/remote_transport/` | Wire contract between local clients and remote provider services |
| Core Provider | `synctv-core/src/provider/<provider>.rs` | Credentials, source configs, targets, dynamic browsing, autoplay, PlaybackResult, proxy resolvers |
| Persistent models | `synctv-core/src/models/source_config.rs`, `provider_target.rs` | Strongly typed source and target values stored by SyncTV |
| Public protobuf | `synctv-proto/proto/source_config.proto`, `providers/`, `playback_provider/` | Contracts consumed by the App, CLI, HTTP, and gRPC |
| API implementation | `synctv-api/src/impls/providers/`, `impls/playback_provider/` | User context, Provider calls, public response mapping |
| Transport registration | `synctv-api/src/http/providers/`, `grpc/providers/`, `openapi.rs` | HTTP, public gRPC, OpenAPI routes and schemas |
| Management and CLI | `synctv-management/`, `synctv/src/cli/` | Remote instances, management RPC, command-line creation and diagnostics |
| Flutter App | `proto/`, `lib/models/`, `lib/services/`, `lib/widgets/add_media/` | Typed codecs, API facade, bindings, preview, selection, creation |

## Implementation Order

<Steps>

1. Define the Provider's actual capabilities and product workflow.
2. Implement the private upstream client, DTOs, and WireMock contract tests.
3. Define persistent source configs, targets, and credential models.
4. Implement Core `MediaProvider`, plus `DynamicPlaylistProvider` when dynamic playlists are supported.
5. Add internal remote-provider protobuf, server, and client transport.
6. Add public source-config, Provider API, and playback-provider protobuf.
7. Wire adapter, management, HTTP, gRPC, OpenAPI, and CLI layers.
8. Sync Flutter protobuf and implement codecs, domain services, bindings, and Add Media UI.
9. Complete unit, contract, Core, API, CLI, Testcontainers, and Flutter tests.
10. Run full verification and request every generated playback resource.

</Steps>

## 1. Upstream Client and DTOs

A Provider directory usually looks like this:

```text
synctv-media-providers/src/example/
├── mod.rs
├── client.rs
├── types.rs
├── client_tests.rs
├── sign.rs          # when the upstream signs requests
└── chat.rs          # when live chat is supported
```

`types.rs` represents upstream JSON, XML, WebSocket, or binary protocols. Field names, optionality, and integer widths should follow real responses. Similar concepts on different platforms still use Provider-specific DTOs and converge only when mapped into SyncTV core structures.

The client owns:

- URL/ID normalization and SSRF boundaries;
- login, refresh, signing, and request headers;
- upstream page, cursor, offset, or continuation rules;
- metadata, cover, thumbnail, subtitle, chapter, and danmaku/chat data;
- native qualities, CDNs, codecs, transcodes, and remux resources;
- mapping platform errors into `ProviderClientError`.

Give every public client method a WireMock or protocol-level unit test. Verify method, path, query, headers/body, and response mapping together.

## 2. Source Configs and Targets

Source configs are persistent playback sources. Define media and playlist sources separately:

```rust
pub struct ExampleMediaSourceConfig {
    pub resource_id: String,
    pub shared: bool,
}

pub enum ExamplePlaylistSourceConfig {
    Channel { channel_id: String, shared: bool },
    Search { query: String, shared: bool },
}
```

Use a distinct variant for every resource type. Provider differences belong directly in the enum. Dynamic source names should be domain names such as `Channel`, `History`, `Favorites`, and `Search`.

`ProviderTarget` stores stable identity for an item inside a dynamic list. Include the smallest field set needed to find that item again. Media source configs generate playback; targets identify list positions, autoplay transitions, and playback-state identity.

Public protobuf uses matching oneofs in `source_config.proto` and `client.proto`. Keep declaration order, field numbers, and generated-code order aligned.

## 3. Credentials and Provider Instances

Credential identity includes:

```text
(user_id, provider, server_id, provider_instance_name)
```

When one host is bound through several instances, scope `server_id` by instance or use another stable instance-aware identifier. Login, list, cover, and playback paths obtain the credential repository through `ProviderContext` fallback:

```rust
let repo = self.credential_repo.as_deref().or(ctx.credential_repo);
```

Before storing media or playlists, `validate_source_config` verifies that the creator owns the referenced credential. `credential_dependencies` returns the dependencies used for cache invalidation and binding deletion protection.

`shared` selects room-owner credential scope. Parse results remain neutral, and the App applies the user's shared-scope choice before creation.

## 4. Parse, Resolve, List, and Preview

Public discovery responses should carry enough data for preview and direct creation:

```proto
message Candidate {
  string title = 1;
  string cover = 2;
  oneof source_config {
    MediaSourceConfig media = 3;
    PlaylistSourceConfig playlist = 4;
  }
}
```

Parse fits Providers where one URL may represent several resources, including multi-part videos, seasons, live rooms, channels, and playlists. Resolve fits a single media URL that returns native format details. List and Search fit platform discovery and NAS browsing.

Every addable preview item should carry a typed source config. Directory items can carry playlist source configs for nested browsing and direct dynamic-playlist creation. The App handles selection and credential scope.

## 5. Pagination

Core uses an explicit enum:

```rust
pub enum DynamicPagination {
    Page { page: u64 },
    Cursor { cursor: Option<String> },
}
```

Public protobuf uses a pagination oneof and reports the mode selected by the upstream:

```proto
message ListResponse {
  repeated Item items = 1;
  oneof pagination {
    PagePagination page = 2;
    CursorPagination cursor = 3;
  }
}
```

Cursors are opaque tokens. The App and Core store and return them unchanged. Offset-based upstreams can map pages to stable offsets. Native cursors can pass through directly or use a versioned envelope.

Sequential autoplay scans across pages until it finds the current target and next media item. A fixed sampling limit fits shuffle. Sequential and repeat-all behavior should keep paging through large folders so playback can advance beyond item 200.

## 6. PlaybackResult and Advanced Resources

`generate_playback` builds the complete playback decision:

- native direct, progressive, DASH, HLS, and FLV modes;
- upstream transcode, remux, CDN, quality, and codec choices;
- `proxy_*` siblings and `default_mode`;
- required headers and Range behavior;
- subtitles, chapters, danmaku/chat, and storyboard;
- covers, thumbnails, and playback metadata;
- URL expiry, cache keys, and refresh context;
- playback start, progress, pause, and stop reporting.

Every proxy URL emitted by the Provider needs a matching `playback_provider` action: redirect, upstream proxy, manifest rewrite, or local stream. Manifest segment and key URLs return to the same Provider resolver.

Source covers resolve credentials from the current `ProviderContext`. Refresh signed thumbnails and short-lived URLs at request time so persistent data remains stable.

### Playback Lifecycle Contract

When playback info creates an upstream session, stream, or transcode, the Provider implements `playback_lifecycle_session_id` and returns a stable ID. Lifecycle state is room-scoped. Active playback uses a 45-second lease and paused playback uses a 10-minute lease; successful progress reports renew the lease.

`on_playback_stop` performs final progress reporting and upstream resource release and returns the actual error. Failed stops remain in the global room index for background retries. Lease expiry and graceful shutdown invoke the same cleanup path. Cleanup operations tolerate repeated calls, and partial success persists only the upstream resources that still require cleanup.

Caches that contain upstream session IDs include the room ID, credential revision, and client capability fingerprint in their keys. A local persistence failure after resource creation triggers immediate compensating cleanup.

## 7. Internal Remote Protocol

Providers that run remotely define an independent service in `synctv-media-providers/proto/` and add:

- protobuf registration in `build.rs`;
- Provider gRPC server;
- client transport in `remote_transport/clients.rs`;
- connector registration and authentication secret;
- aligned error semantics for local and remote paths;
- protobuf contract tests.

The internal remote protocol and public SyncTV API use separate packages. Public APIs live under `synctv-proto/proto/providers/` and are served by the main SyncTV server.

## 8. HTTP, gRPC, and OpenAPI

Complete these registrations for a public Provider API:

1. Shared implementation in `synctv-api/src/impls/providers/<provider>.rs`.
2. HTTP routes and `utoipa::path` in `http/providers/<provider>.rs`.
3. Public gRPC service in `grpc/providers/<provider>.rs`.
4. Router and service registration in `http/providers/mod.rs` and `grpc/mod.rs`.
5. Paths and schemas in `openapi.rs`.
6. Rate-limit category, authentication, and instance-name extraction.

HTTP and gRPC call the same impl. OpenAPI responses use the public protobuf structure to keep one transport-independent DTO contract.

## 9. Flutter App

After syncing public protobuf, regenerate Dart code:

```bash
cd /Volumes/workspace/flutter/synctv-app
dart pub global activate protoc_plugin
bash tool/generate_proto.sh
```

App integration order:

1. Add a Provider-specific source-config helper and domain models under `lib/models/`.
2. Implement protobuf/App-map round trips in `SourceConfigCodec`.
3. Add the HTTP facade in `synctv_api_facades.dart`.
4. Map protobuf into domain models in `synctv_provider_service.dart`.
5. Expose stable calls through `synctv_service.dart`.
6. Implement bind, capability display, and unbind in `platform_binding_dialog.dart`.
7. Implement parse, preview, selection, and creation in `widgets/add_media/<provider>_add_media_form.dart`.
8. Register it in `add_media_dialog.dart` and gate Cookie/scope-dependent sources by binding capability.

Use an independent mode enum and state model for each Provider UI. Consume server-returned typed configs. Support page/cursor load-more behavior, use App component wrappers, and verify narrow and desktop layouts.

## 10. Test Matrix

| Layer | Required coverage |
| --- | --- |
| Client | WireMock request contracts, signing, URL normalization, response variants, error envelopes |
| Internal proto | Service/method/message/field oneofs and local/remote transport |
| Core | Config validation, credential instance scope, target round trip, pagination, covers, autoplay |
| Playback | Direct/proxy modes, Range, manifests/segments, subtitles, danmaku, expiry, refresh |
| Public API | HTTP, OpenAPI, public gRPC registration, typed response configs |
| CLI | JSON-to-protobuf oneofs and discovery/bind/create commands |
| Database | Testcontainers credential encryption, persistence, and instance binding |
| Flutter | Codecs, domain services, binding widgets, preview/create widgets, UI guard |

Run the complete verification set:

```bash
cd /Volumes/workspace/rust/synctv
cargo +nightly fmt --all
cargo +nightly check --workspace --all-targets
make nextest

cd /Volumes/workspace/flutter/synctv-app
dart format lib test
dart analyze
flutter test
```

`make nextest` uses the project's nightly/Testcontainers workflow and runs ignored integration tests. Use mocked upstreams for network contracts and fixed Testcontainers images for self-hosted compatibility tests.

## Completion Checklist

- [ ] Provider DTOs, client, signing, and error mapping are isolated.
- [ ] Every valuable upstream capability maps to a typed source or playback capability.
- [ ] Parse/List/Preview responses carry directly submitable typed source configs.
- [ ] Media and playlist configs and targets round trip through JSON and protobuf.
- [ ] Page, cursor, offset, or continuation behavior is explicit in responses.
- [ ] Sequential and repeat playback cross large-folder boundaries.
- [ ] Credentials use user/provider/server/instance scope and resolve through `ProviderContext`.
- [ ] Covers, thumbnails, subtitles, danmaku, manifests, and segments have resolvers.
- [ ] Local and remote Provider behavior is aligned.
- [ ] HTTP, gRPC, OpenAPI, management, and CLI registrations are complete.
- [ ] The App supports binding, capability gating, URL parsing, preview, partial selection, and dynamic-playlist creation.
- [ ] WireMock, Core, API, CLI, Testcontainers, and Flutter tests pass.
