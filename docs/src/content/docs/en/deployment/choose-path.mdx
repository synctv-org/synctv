## Choose First, Then Copy Commands

The default recommendation is **single-node production Compose**. It is the right first path for most deployments and for long-running service on one machine. Choose another path only when you are changing code, doing temporary evaluation, or already operating on Kubernetes.

## Path Comparison

| Path | Best for | Startup style | Production fit | Next page |
| --- | --- | --- | --- | --- |
| Single-node production Compose | Self-hosters, small teams, one server | Prebuilt image + `.env.postgres` + `.env.synctv` | Recommended default | [Quick Start](../../guides/quick-start/) |
| Local evaluation | Temporary UI or feature preview | `docker-compose.dev.yml` | Not for public or long-running use | [Quick Start: local evaluation](../../guides/quick-start/#b-local-evaluation) |
| Source run | Developers, API debugging, code changes | Container dependencies + local `cargo run` | Not a deployment path | [Development Guide](../../guides/development/) |
| Helm/Kubernetes | Multi-replica or platform teams | Helm values + Kubernetes Secret/PVC/Ingress | Production capable, higher complexity | [Helm Deployment](../helm/) |

## Default Path: Single-Node Production Compose

Choose it if any of these are true:

- You have one server, NAS, or VM.
- You want the shortest path to a long-running SyncTV instance.
- You do not want to start with Kubernetes, Ingress controllers, PVCs, or Secret operators.
- You can manage PostgreSQL backups and a few long-lived secrets.

Success signals:

- `.env.postgres` and `.env.synctv` are persisted and backed up.
- `docker compose config` passes.
- `/health/ready` returns 200.
- The root user can log in.
- PostgreSQL has a backup plan.

## When Not to Choose the Default

<CardGrid>
  <Card title="Temporary evaluation" icon="rocket">
    Use local evaluation. It is fast, but it uses development secrets and must not be exposed publicly or kept long term.
  </Card>
  <Card title="Source changes" icon="puzzle">
    Use a source run. PostgreSQL and Redis can come from development Compose, while SyncTV runs from the local Rust toolchain.
  </Card>
  <Card title="Existing Kubernetes platform" icon="cloud-download">
    Use Helm. Decide HTTP/gRPC Ingress, Secret, PVC, metrics, Redis, HLS storage, and rolling-update boundaries first.
  </Card>
  <Card title="Multi-replica realtime" icon="setting">
    Use Helm or a self-managed multi-replica deployment with cluster mode. Every replica must share PostgreSQL, Redis, and the same cluster secret.
  </Card>
</CardGrid>

## Decision Rules

<Steps>
1. If it faces users, do not use development Compose secrets.
2. If it runs long term, back up PostgreSQL and production secrets.
3. If it runs multiple replicas, share PostgreSQL, Redis, `redis.key_prefix`, and `server.cluster_secret`.
4. If HLS runs across replicas, choose publisher-node proxying, `shared_file`, or OSS explicitly.
5. If the management plane uses TCP, configure a token and keep it away from normal public entrypoints.
</Steps>

<Aside type="tip">
When unsure, choose single-node production Compose. It is the smallest production loop and can still be migrated to Helm or another orchestrator later.
</Aside>
