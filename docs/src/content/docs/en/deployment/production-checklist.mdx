## How To Use This Checklist

This page is a launch checklist, not a field-by-field configuration reference. Complete the required section first, then the recommended section, then the as-needed items for WebAuthn, OAuth2, email, livestreaming, HLS, STUN, and slice cache.

If you have not reviewed the component boundaries yet, start with [Architecture Overview](../../guides/architecture/). If you are designing login, 2FA, OAuth2, or management control-plane policy, read [Authentication and Security Model](../../guides/security-model/).

## Required

| Check | Acceptance Criteria |
| --- | --- |
| JWT secret | `jwt.secret` is injected through a secret mechanism and is not an example value. |
| OPAQUE setup secret | `security.opaque_server_setup_secret` is generated, backed up, and stable across deployments. |
| Credential encryption key | `security.credential_encryption_key` is generated, backed up, and is 64 hex characters. |
| Initial root password | Comes from `SYNCTV_BOOTSTRAP_ROOT_PASSWORD` or a secret file, not Git. |
| PostgreSQL persistence | PostgreSQL uses persistent storage. |
| PostgreSQL backups | Backups exist and the restore order is known. |
| Config validation | `synctv config validate` passes. |
| Database migrations | `synctv db status` or startup logs confirm embedded SQLx migrations are healthy. |
| Health check | `/health/ready` succeeds after startup. |
| TLS | Public entrypoints use TLS. |
| Management control plane | Not exposed to normal public clients. |

Required secret generation:

| Secret | Purpose | Generation |
| --- | --- | --- |
| `jwt.secret` | Signs access, refresh, and guest tokens | `openssl rand -base64 32` |
| `security.opaque_server_setup_secret` | OPAQUE password authentication | `openssl rand -base64 48` |
| `security.credential_encryption_key` | Encrypts provider credentials; 64 hex chars | `openssl rand -hex 32` |
| `server.cluster_secret` | Inter-node auth; required in cluster mode | `openssl rand -hex 32` |
| `bootstrap.root_password` | Initial root user password | Password manager |

<Aside type="caution">
The OPAQUE setup secret and provider credential encryption key are long-lived keys. Losing or casually rotating them can break existing password records or stored provider credentials.
</Aside>

## Recommended

| Check | Acceptance Criteria |
| --- | --- |
| Redis | Configured for rate limits, token blacklist, OAuth2 state, WebAuthn challenges, L2 cache, and cluster short-lived state. |
| Redis key prefix | `redis.key_prefix` does not collide with test, staging, or another production environment. |
| Logs | JSON logs or another format your logging stack can parse reliably. |
| Metrics auth | Metrics are enabled with bearer/basic/Kubernetes authentication. |
| Metrics exposure | `/metrics` is not publicly exposed. |
| Alerts | Cover PostgreSQL, Redis, login failures, MFA failures, WebSocket, providers, proxy, livestreaming, and cluster behavior. |
| Reverse proxy/Ingress | Supports WebSocket and has appropriate timeouts. |
| Trusted proxies | `server.trusted_proxies` trusts only proxy networks you control. |
| Rolling updates | Kubernetes termination grace period is longer than `server.shutdown_drain_timeout_seconds`. |
| Upgrade validation | Staging validates migrations, login, room reads/writes, realtime connections, and provider access. |

## As Needed

| Feature | Acceptance Criteria |
| --- | --- |
| CORS | Configure `server.cors_allowed_origins` when web frontend and API are on different origins. Use origins only, no paths. |
| Passkeys/WebAuthn | Configure production `rp_id` and `rp_origin`, and verify they match the real HTTPS entrypoint users open in the browser. |
| Email | Configure SMTP and test `synctv settings test-email` when email verification, password reset, email MFA, or notifications are used. |
| OAuth2 | Configure providers in runtime settings and match `redirect_url` with provider registration. |
| Multi-replica shared state | All replicas share the same PostgreSQL, Redis, and `redis.key_prefix`. |
| Cluster mode | Configure `server.cluster_secret` and `server.advertise_host`. |
| Public gRPC | Split HTTP and gRPC Services/Ingresses on Kubernetes. |
| Livestreaming/STUN | Expose RTMP; for built-in STUN, expose UDP 3478. |
| Multi-replica HLS | Explicitly use publisher-node proxy, `shared_file`, or OSS. |
| File-backed slice cache | Mount a directory with enough capacity and a cleanup policy. |
| OpenAPI | Decide whether production should expose `/swagger-ui/` and `/api-docs/openapi.json`. |

## Key Snippets

### CORS and Trusted Proxies

```yaml
server:
  cors_allowed_origins:
    - "https://app.example.com"
  trusted_proxies:
    - "10.0.0.0/8"
```

`cors_allowed_origins` accepts origins such as `https://app.example.com`, not paths such as `https://app.example.com/app`.

### WebAuthn/passkeys

```yaml
webauthn:
  enabled: true
  rp_id: "example.com"
  rp_origin: "https://app.example.com"
```

`rp_origin` must be the exact HTTPS origin users visit. `rp_id` must be the same domain or a valid parent domain.

### Email

```yaml
email:
  smtp_host: "smtp.example.com"
  smtp_port: 587
  smtp_username: "noreply@example.com"
  smtp_password_file: "/run/secrets/smtp_password"
  from_email: "noreply@example.com"
  from_name: "SyncTV"
  use_tls: true
```

Test:

```bash
synctv settings test-email admin@example.com
```

### gRPC Ingress

For Nginx Ingress:

```yaml
ingress:
  grpc:
    annotations:
      nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
```

HTTP REST and public gRPC share the process port, but Kubernetes deployments should expose them through separate Services and Ingresses.

### HLS Storage

Shared filesystem:

```yaml
livestream:
  hls_storage_backend: "shared_file"
  hls_storage_path: "/var/lib/synctv/hls"
```

Object storage:

```yaml
livestream:
  hls_storage_backend: "oss"
  hls_oss:
    endpoint: "https://s3.example.com"
    bucket: "synctv-hls"
    access_key_id_file: "/run/secrets/hls_oss_access_key_id"
    secret_access_key_file: "/run/secrets/hls_oss_secret_access_key"
```

### Proxy Slice Cache

```yaml
proxy_slice_cache:
  enabled: true
  file_backend_enabled: true
  file_cache_dir: "cache/proxy-slice"
```

Slice cache stores Range slices only. Upstreams that do not support Range are bypassed; full-body cache is not used.

## Launch Verification

### Binary or systemd

```bash
synctv config validate
synctv db status
curl -fsS http://localhost:8080/health/ready
```

### Docker Compose

```bash
docker compose config
docker compose up -d
docker compose ps
docker compose exec synctv synctv db status
curl -fsS http://localhost:8080/health/ready
```

For production Docker Compose, first get `docker-compose.yml` and the env init script from [Docker Compose Deployment](../docker-compose/#get-production-compose-files), then keep `.env.postgres` and `.env.synctv` in the Compose file directory.

### Helm

```bash
helm lint ./helm/synctv
helm template synctv ./helm/synctv
helm status synctv -n synctv
kubectl -n synctv rollout status deploy/synctv
kubectl -n synctv get pods
```

## Backups

Must back up:

- PostgreSQL.
- Production secrets.

Back up as needed:

- HLS `shared_file` storage.
- Proxy slice cache.
- Custom configuration files.

Redis is usually short-lived shared state, but losing it can affect OAuth2 state, token blacklist, rate-limit counters, WebAuthn challenges, and cluster short-lived state.

For restore order and restore drills, see [Backup and Restore](../../operations/backup-restore/).

## Upgrades

Before upgrade:

- Back up PostgreSQL.
- Preserve all secrets.
- Start the target version in a test environment first and verify automatic migrations plus business reads/writes.
- Check [Configuration Index](../../reference/configuration-index/), [Full Configuration Example](../../configuration/full-example/), Compose, and Helm values for new fields.
- If OpenAPI is enabled, confirm generated clients are compatible with API changes.

For Kubernetes rolling updates, configure readiness, termination grace period, and `server.shutdown_drain_timeout_seconds` so long-lived connections are not cut abruptly.

For migrations, Helm/Compose releases, rolling updates, and rollback strategy, see [Upgrades and Migrations](../../operations/upgrades/).
