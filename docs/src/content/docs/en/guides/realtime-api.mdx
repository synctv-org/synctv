## When to Use It

The Realtime API is the room-scoped long-lived connection protocol. It is used for chat, danmaku, playback commands, playback progress, WebRTC signaling, and subscribing to changes in cacheable room resources.

Use HTTP/OpenAPI or gRPC for one-shot reads and writes. Use the Realtime API when you need low-latency push, less polling, or continuously synchronized room state.

## Transport and Authentication

WebSocket URL:

```text
wss://<host>/ws/rooms/<room_id>
```

Authentication options:

| Method | Clients | Notes |
| --- | --- | --- |
| `Authorization: Bearer <access_token>` | Native clients, CLI, server-side SDKs | Recommended because the token is not placed in the URL. |
| `?ticket=<ticket>` | Browsers and clients that cannot set headers | First call `POST /api/tickets` to create a short-lived, one-time-use, room-bound ticket. |

WebSocket only handles binary protobuf frames. Clients send `synctv.client.ClientMessage`, and the server returns `synctv.client.ServerMessage`. Text frames, ping, pong, and other non-business frames are not processed as business messages.

```js
const roomId = 'room_1';
const ticket = ticketResponse.ticket;
const ws = new WebSocket(`wss://app.example.com/ws/rooms/${roomId}?ticket=${ticket}`);
ws.binaryType = 'arraybuffer';

ws.onmessage = async (event) => {
  const bytes =
    event.data instanceof Blob
      ? new Uint8Array(await event.data.arrayBuffer())
      : new Uint8Array(event.data);
  const message = ServerMessage.decode(bytes);
  handleServerMessage(message);
};

function sendClientMessage(message) {
  ws.send(ClientMessage.encode(message).finish());
}
```

<Aside type="caution">
Do not put refresh tokens in WebSocket URLs. Browser clients should use WebSocket tickets; do not reuse a ticket after success or failure.
</Aside>

## Base Messages

All Realtime API business messages live in the `ClientMessage.message` and `ServerMessage.message` `oneof` fields.

Common client messages:

| `ClientMessage` field | Purpose |
| --- | --- |
| `chat` | Send chat or danmaku messages. |
| `heartbeat` | Client heartbeat. |
| `playback_progress` | Report current playback position and play/pause state. |
| `playback_update` | Send a playback state update command. |
| `webrtc_offer` / `webrtc_answer` / `webrtc_ice_candidate` | Forward WebRTC signaling. |
| `webrtc_join` / `webrtc_leave` | Join or leave a WebRTC session. |
| `observe_resource` | Subscribe to a realtime resource. |
| `unobserve_resource` | Unsubscribe from a realtime resource. |

Common server messages:

| `ServerMessage` field | Purpose |
| --- | --- |
| `chat` | Chat or danmaku received. |
| `heartbeat_ack` | Heartbeat acknowledgement. |
| `error` | General business error. |
| `playback_state` / `playing_changed` | Playback state or playback target changed. |
| `room_settings` | Room settings changed. |
| `media_added` / `media_updated` / `media_removed` / `media_removed_batch` | Media changes. |
| `playlist_created` / `playlist_updated` / `playlist_deleted` / `playlist_reordered` | Playlist changes. |
| `permission_changed` / `user_joined` / `user_left` / `room_members` | Member and permission changes. |
| `webrtc_offer` / `webrtc_answer` / `webrtc_ice_candidate` / `webrtc_join` / `webrtc_leave` | WebRTC signaling or member state. |
| `resource_observed` / `resource_changed` / `resource_observe_error` | Realtime resource observation result. |

Use `synctv-proto/proto/client.proto` as the source of truth for complete field definitions.

## Resource Observation Model

Resource observation subscribes to cacheable query results. The client submits its cached version, and the server decides whether the resource changed. When it changes, the server can push a full snapshot or only notify the client to re-fetch.

Supported resources:

| Resource | `ObserveResource.resource` field | Version source | Typical use |
| --- | --- | --- | --- |
| Playback state | `playback_state` | `RoomPlaybackState.version` | Player UI and synchronized playback status. |
| Playback snapshot | `playback_snapshot` | `PlaybackSnapshot.version` | Current playback source URL, headers, proxy policy, and expiration. |
| Room settings | `room_settings` | Room settings version | Chat, danmaku, playback permissions, and UI controls. |
| Playlist items | `playlist_items` | List snapshot version | Root lists, child playlists, provider browsing, and search results. |
| Room members | `room_members` | Member list snapshot version | Member pagination, search, role filtering, and status filtering. |

Each observation is identified by `observe_id`. It only needs to be unique within the current connection, length 1-128. Prefer stable names such as `playback-state`, `playlist-root:p1:50`, or `members:online`.

Each connection can hold up to 64 observations. Over-limit requests return `ResourceObserveError` and do not close the WebSocket.

## Delivery Mode

`ObserveResource.delivery_mode` controls what is pushed when a resource changes:

| Value | Behavior |
| --- | --- |
| `RESOURCE_DELIVERY_MODE_UNSPECIFIED` | Same as `PUSH_SNAPSHOT`. |
| `RESOURCE_DELIVERY_MODE_PUSH_SNAPSHOT` | Push a full `ResourceChanged.payload` when changed. Recommended for low-latency UI updates. |
| `RESOURCE_DELIVERY_MODE_NOTIFY_ONLY` | Push only `changed_only`. The client should fetch the resource through HTTP/gRPC. Useful for large lists, low-frequency background sync, or clients with their own cache layer. |

## Subscribe Flow

<Steps>
1. The client connects to the room WebSocket.
2. The client sends `ClientMessage.observe_resource` with `observe_id`, local cached `version`, `delivery_mode`, and the target resource.
3. The server loads the current resource and sends `ServerMessage.resource_observed`.
4. If the server determines that the resource changed, it then sends `ServerMessage.resource_changed` for the same `observe_id`.
5. While connected, later room events, cache invalidation, provider credential changes, and playback snapshot expiration can trigger resource re-evaluation.
</Steps>

`ResourceObserved` fields:

| Field | Meaning |
| --- | --- |
| `observe_id` | The submitted subscription ID. |
| `version` | The current server-side version. Save it for reconnects or later subscriptions. |
| `changed` | Whether the server-side resource differs from the submitted `version` or playback snapshot source identity. |

`ResourceChanged` fields:

| Field | Meaning |
| --- | --- |
| `observe_id` | Which subscription changed. |
| `version` | New version. Update the local cached version. |
| `payload` | Full snapshot or `changed_only`, depending on `delivery_mode`. |

## Unsubscribe

When a view, list, or query is no longer needed, send `ClientMessage.unobserve_resource`:

```ts
sendClientMessage({
  unobserveResource: {
    observeId: 'playlist-root',
  },
});
```

There is no acknowledgement for unsubscribe. When the WebSocket disconnects, the server automatically clears all observations for that connection.

## Handling Server Messages

Clients should dispatch by `oneof` type, not by text fields or log strings:

```ts
function handleServerMessage(message) {
  if (message.resourceObserved) {
    cacheVersion(message.resourceObserved.observeId, message.resourceObserved.version);
    return;
  }

  if (message.resourceChanged) {
    const changed = message.resourceChanged;
    cacheVersion(changed.observeId, changed.version);

    if (changed.playlistItems) {
      replacePlaylistCache(changed.observeId, changed.playlistItems);
    } else if (changed.changedOnly) {
      scheduleRefetch(changed.observeId);
    }
    return;
  }

  if (message.resourceObserveError) {
    logObserveError(message.resourceObserveError);
  }
}
```

Legacy broadcast messages still exist, such as `media_added`, `playlist_updated`, `room_settings`, and `playback_state`. New clients can use resource observation to maintain final UI snapshots, and use legacy broadcasts for lightweight hints, animations, or compatibility logic.

## Change Triggers

The server refreshes observations based on events:

| Event type | Refreshed resources |
| --- | --- |
| Playback state changed | `playback_state`, `playback_snapshot` |
| Current playback media or playlist-related media updated | `playback_snapshot`, and sometimes `playlist_items` |
| Playlist created, updated, deleted, reordered, or media added/removed | `playlist_items` |
| Room settings changed | `room_settings`, `room_members` |
| User joined, left, or permissions changed | `room_members` |
| Cache invalidation hits the current room or user | Matching playback, settings, list, or member resources |
| Provider credential changed | May affect the current user's playback snapshot and provider browsing results |
| Playback snapshot expires | Automatically re-evaluates `playback_snapshot` observations |

The server coalesces identical short-window queries in the same room, which reduces duplicate snapshot loads when multiple connections subscribe to the same resource. Clients do not need to rely on this optimization, but can safely create separate `observe_id` values for separate views.

## Reconnect Strategy

Observations are not retained across WebSocket connections. After disconnect, clients should:

<Steps>
1. Request a new WebSocket ticket, or reconnect with a valid access token.
2. Re-send `observe_resource` for currently visible views.
3. Include the locally saved `version` so the server can decide whether to send a snapshot.
4. For `playback_snapshot`, also include cached `media_id`, `playlist_id`, `target`, and `playback_client_profile`.
5. Keep the local cache when `resource_observed.changed=false`; replace it when `resource_changed` arrives.
</Steps>

If the connection has been down for a long time, fetch critical resources through HTTP/gRPC first, then restore observations. This avoids showing stale UI for too long.

## Error Handling

Resource observation errors are returned as `ServerMessage.resource_observe_error`:

| Scenario | Client action |
| --- | --- |
| Empty `observe_id` or longer than 128 characters | Fix client code. Do not retry the same request. |
| Missing `resource` | Fix client code. |
| More than 64 observations on one connection | Unobserve unused resources or merge list views. |
| Snapshot service unavailable or load failed | Show a temporary error and retry with backoff if useful. |
| Permission, missing resource, or invalid input error | Re-fetch room state and navigate back when needed. |

If sending fails or the server closes the connection, do not assume observations remain active. Rebuild all observations after reconnecting.

## Compatibility Notes

The current protocol uses `ClientMessage.observe_resource = 19` and `ClientMessage.unobserve_resource = 20`. The old watch field range `14` to `18` is reserved and should not be used by new clients. After generating client code, use `ObserveResource` as the resource subscription entry point.
